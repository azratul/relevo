# Relevo protocol 1.0 (normative)

This document defines the protocol **semantics**. The **shape** of every message and body is defined by the schemas, which are the source of truth:

| Part | File |
|---|---|
| HTTP | [`api/openapi.yaml`](../api/openapi.yaml) (OpenAPI 3.1.1) |
| WebSocket and DataChannel messages | [`api/asyncapi.yaml`](../api/asyncapi.yaml) (AsyncAPI 3.0.0) |
| Messages and bodies | [`api/schemas/`](../api/schemas) (common subset of JSON Schema draft-07 and 2020-12, [ADR-0012](adr/0012-schema-dialect.md)) |
| Examples | [`api/examples/`](../api/examples) (valid and invalid, checked in CI) |

If this text and a schema disagree about the shape of a message, the schema wins and the text is a bug. MUST, MUST NOT and MAY are normative.

The relay runs inside `relevo-host` and is published through the tunnel the host chose ([ADR-0001](adr/0001-embedded-relay-and-host-chosen-tunnel.md)); the contract does not depend on that.

## 1. Versions

- The **application version** (e.g. `0.1.0` of the binary) and the **protocol version** (`MAJOR.MINOR`, currently `1.0`) are independent. `GET /api/v1/info` publishes the supported protocol versions and capabilities.
- Every WebSocket/DataChannel message carries `protocolVersion`. The relay accepts any `1.x`; another major version gets `UNSUPPORTED_VERSION` (on `auth.hello`: `auth.error` and close 4002).
- `auth.ok.protocolVersion` is the relay's version. A client MUST NOT send fields introduced in a minor version newer than the relay's.
- **Compatibility**:
  - Messages *received* by the relay (from controllers and hosts) are strict: unknown fields → `INVALID_MESSAGE`. A speaker cannot smuggle fields such as `issuedBy` or `actorId`.
  - Messages *sent* by the relay may gain optional fields in a minor version; receivers MUST ignore unknown fields.
  - Adding an optional message type, an error code, an action or an optional outbound field is a minor change. Removing something or changing its meaning is a major change (new `/api/v2` prefix).
  - Receivers MUST treat unknown error codes as not retryable unless `retryable` says otherwise.
- HTTP is versioned by path (`/api/v1`).

## 2. Roles and credentials

| Credential | Obtained from | Scope | Kept in |
|---|---|---|---|
| Session password | Chosen by the host or generated (≈59 bits, `xxxx-xxxx-xxxx`) | Only for `join` | Told by the host through a channel other than the link. The relay keeps only a salted Argon2id hash |
| Host token `rlvh_…` | `POST /sessions` response (once) | The whole session, host role | Memory of `relevo-host`. Never sent to a speaker's browser; not derived from the password |
| Speaker token `rlvp_…` | `join` response | One session, controller role, one participant | Memory of the remote (reloading means joining again) |
| Creation token `rlvc_…` | Generated by `relevo-host` at start-up | Only `POST /sessions` | Memory of `relevo-host`; nobody on the Internet can create sessions |

Tokens are 256 random bits (CSPRNG) and opaque; the relay stores their SHA-256. They **never** go into URLs, QR codes, query strings or logs: HTTP uses `Authorization: Bearer`; WebSocket and DataChannel use the first message.

### Lifecycle

| Event | Effect |
|---|---|
| Session expiry (TTL, 8 h by default, 24 h max) | Session closed (`session.closed: expired`); every credential dies |
| Host absent longer than `HostIdleTimeout` (30 min) | Session closed (`idle`) |
| Speaker token expiry (min(session TTL, 12 h)) | Revoked (`expired`); `AUTH_EXPIRED` |
| Logout (`POST /leave`) | Token revoked; the official remote also does it on `pagehide` |
| Removal by the host (`state: revoked`) | Token revoked, socket closed after `session.closed: revoked` with code 4003. Final: to come back the speaker joins again with the password |
| Disable (`state: disabled`) | The token still shows the state; commands are rejected (`PERMISSION_DENIED`) |
| Password rotation | Every speaker revoked (`password-rotated`); the host keeps its token |
| End of session (`DELETE`) | Every credential dies; every socket gets `session.closed: host-ended` and is closed (4004) |
| Quitting `relevo-host` | The session ends ([ADR-0009](adr/0009-ephemeral-state-and-limits.md)) |
| Network loss | Credentials stay valid; the client reconnects with the same token |

### Manual approval

With `requireApproval`, a successful `join` creates the participant as `pending`: it can connect and see its own state, but its commands get `PERMISSION_DENIED` until the host sets it to `enabled`.

### Session creation

`POST /sessions` requires the creation token generated by `relevo-host`; from the Internet it answers `AUTH_FAILED`. The embedded relay holds a single session.

## 3. Connections

Endpoint: `GET /api/v1/ws`, same origin as the remote (the tunnel's public URL). One JSON message per text frame. Binary frames → close 4000.

1. **Origin**: if the request carries `Origin`, it MUST exactly match the allowed list (the origin of the current public URL); otherwise `403` before the upgrade. Native clients send no `Origin` and still need a credential: Origin is not authentication.
2. **Authentication in the first message**: the client MUST send `auth.hello` with its token within `AuthTimeout` (5 s). Before that the relay reveals nothing and accepts no commands. Errors: `auth.error` and close (4001 credential/timeout, 4002 version, 4000 malformed message).
3. **Order after authentication**: the relay sends exactly `auth.ok` and then `session.snapshot`; updates follow. No other message precedes `auth.ok`.
4. **Identity**: role and participant come from the authenticated connection. The relay never trusts identities in payloads. The envelope's `sessionId` MUST match the authenticated session.
5. **One connection per credential**: a new connection with the same token replaces the previous one (close 4009). For the host this also fences the previous epoch (§6).

### Heartbeat and stalled links

- The relay sends WebSocket *ping* frames every `heartbeat.intervalMs` (15 s) and closes the connection if no *pong* arrives within `HeartbeatTimeout` (10 s).
- Browsers cannot send ping frames, hence the **application** `ping`/`pong` (JSON messages). The official remote sends `ping` periodically and, without a `pong` within `heartbeat.timeoutMs`, closes and reconnects.
- The host uses the same application `ping` as a **lease**: after 15 s without `pong` it stops executing and reconnects, even if TCP looks open.

### Limits (defaults)

| Limit | Value | When exceeded |
|---|---|---|
| Message size | 16 KiB (`auth.ok.limits.maxMessageBytes`) | Close 1009 |
| Messages per connection | 20/s, burst 40 | `error RATE_LIMITED`; after 20 warnings, close 4008 |
| Commands per speaker | 5/s, burst 10 | `command.rejected RATE_LIMITED` |
| Commands in flight per session | 8 | `command.rejected RATE_LIMITED` |
| Host queue | 16 | `command.result rejected RATE_LIMITED` |
| Connections | 1000 unauthenticated in total; 30 per IP (200 when the tunnel does not pass client IPs) | `429` before the upgrade |
| Speakers per session | 50 | `join` → `RATE_LIMITED` |
| HTTP body | 8 KiB (32 KiB for an SDP offer) | `INVALID_MESSAGE` |
| Login attempts | 10/min per IP; after 5 failures per session+IP, exponential lockout from 1 s up to 5 min (up to 10 s when the tunnel does not pass client IPs, so one person cannot lock everybody out) | `429` + `Retry-After` |

A message dropped by the per-connection message limit (not the command limit) gets no `command.rejected`: the client can ask for its status with `command.status.request`.

### Memory cleanup

A closed connection frees its outbound queue. Closed sessions are removed on the next sweep (5 s). Deduplication records live with the speaker (at most 256 each). Rate-limit tables drop idle keys.

### WebRTC DataChannel transport (optional, [ADR-0014](adr/0014-webrtc-datachannel-without-turn.md))

- If `auth.ok.capabilities` contains `webrtc`, `auth.ok.rtc.iceServers` lists STUN servers. The controller MAY open an `RTCPeerConnection` with them, create **one** reliable and ordered DataChannel labelled `relevo` (no `maxRetransmits`/`maxPacketLifeTime`), gather every candidate and post the offer to `POST /api/v1/sessions/{id}/rtc` with its token. The answer contains the complete SDP (no trickle ICE). Limit: one offer every 2 s per speaker (burst 3).
- The DataChannel carries the same JSON envelopes (one text message each). The first MUST be `auth.hello` (same deadline and rules as WebSocket). Once it authenticates, the relay closes the speaker's previous connection with 4009; the controller MUST treat that 4009 as expected.
- An unreliable or unordered DataChannel, a binary message, a message larger than `maxMessageBytes`, or losing ICE connectivity (≈8 s without consent) closes the channel. DataChannels have no close codes: the relay sends `auth.error` or `session.closed` first when applicable.
- If ICE does not connect or the channel closes, the controller MUST stay on (or return to) the WebSocket and query its pending commands with `command.status.request`. Changing transport never resends commands.
- There is no TURN: the tunnel's WebSocket is the fallback.

### Tunnel restarts

If the tunnel restarts with a new public URL, the relay adopts it: previous links and Origins stop working and the host must share the new link. Sessions and credentials are kept.

## 4. Common envelope

```json
{ "protocolVersion": "1.0", "type": "command.request", "messageId": "<uuid>",
  "sessionId": "<id>", "correlationId": "<uuid>", "payload": { } }
```

- `messageId`: a unique UUID per message, chosen by the sender.
- `correlationId`: in replies, the request's `messageId` (`auth.ok`→`auth.hello`, `command.accepted|rejected|result`→`command.request`, `command.status`→`command.status.request`, `host.registered`→`host.register`, `pong`→`ping`, `error`→the offending message when its `messageId` was readable).
- `sessionId`: required except in `ping`, `pong`, `auth.error` and `error`.

## 5. Messages: who and when

| Type | Sender → receiver | Required state |
|---|---|---|
| `auth.hello` | controller/host → relay | First message of the connection |
| `auth.ok` / `auth.error` | relay → controller/host | Reply to `auth.hello` |
| `host.register` | host → relay | Authenticated as host. Starts a new epoch |
| `host.registered` | relay → host | Reply to `host.register` |
| `host.update` | host → relay | Host registered on this connection |
| `session.snapshot` | relay → everyone | Right after `auth.ok` |
| `session.updated` | relay → everyone | After any visible change (pause, host, catalog, approval) |
| `session.closed` | relay → everyone | The connection's credentials ended; the socket closes next |
| `participant.updated` | relay → host (anyone) / controller (itself only) | Join, state or capability change, connect/disconnect |
| `command.request` | controller → relay | Authenticated as a speaker |
| `command.accepted` / `command.rejected` | relay → issuing controller | Reply to `command.request` |
| `command.dispatch` | relay → executing host | Current epoch |
| `command.result` (host) | host → relay | One per dispatch received |
| `command.result` (controller) | relay → issuing controller | After the host's result, a timeout or the loss of the host |
| `command.status.request` / `command.status` | controller ↔ relay | Any time after authentication |
| `ping` / `pong` | client → relay / relay → client | Any time after authentication (before it, only `auth.hello` is accepted) |
| `error` | relay → anyone | Malformed message, wrong role, limit |

A role sending a type it may not send gets `error FORBIDDEN`.

## 6. Host, epochs and fencing

- There is **one executing host** per session. Every accepted `host.register` increments the **epoch** and returns it in `host.registered`.
- A new host connection (same token) closes the previous one with 4009; commands dispatched to the previous epoch become `unknown`.
- The host MUST ignore dispatches whose `epoch` is not current or whose `sequence` is not greater than the last one seen in the epoch.
- The host announces `ready` and `readinessReason` (missing permission, target window not found…). With `ready=false` the relay rejects commands with `HOST_NOT_READY`.

## 7. Commands

### 7.1 Lifecycle

```
            ┌──────── rejected by the relay ────────► rejected (final, never executed)
request ────┤
            └─► accepted ─► dispatched ─┬─► executed  (final; see confirmation level)
              (sequence                 ├─► failed    (final; the adapter did not do it)
               assigned)                ├─► rejected  (final; the host refused without executing)
                                        ├─► expired   (final; expired in the host queue)
                                        └─► unknown   (final; cannot know whether it ran)
```

Transient states: `accepted`, `dispatched` (in `command.status`). Final: `executed`, `failed`, `rejected`, `expired`, `unknown`. A final state never changes, not even if a late host result arrives (it is logged and ignored).

### 7.2 Validation in the relay (normative order)

1. Deduplication by the speaker's `commandId` (§7.4).
2. `clientSequence` must be greater than the speaker's last one; otherwise → `COMMAND_EXPIRED`.
3. Speaker state: `pending`/`disabled` → `PERMISSION_DENIED`.
4. Speaker quota → `RATE_LIMITED`.
5. Session paused → `SESSION_PAUSED`.
6. Host not connected → `HOST_OFFLINE`; not ready → `HOST_NOT_READY`. **Nothing is queued for an offline host**: the command is rejected at once.
7. `catalogRevision` differs from the current one → `STALE_CATALOG`.
8. Action not announced → `UNSUPPORTED_ACTION`; capability not granted → `PERMISSION_DENIED`.
9. Parameters checked against the action's schema → `INVALID_MESSAGE`.
10. Commands in flight ≥ limit → `RATE_LIMITED`.

If everything passes, the relay assigns the next **session sequence**, answers `command.accepted` and sends `command.dispatch`, both under the same session lock: **total order per session**. With two speakers, dispatch order is arrival order at the relay, visible in `sequence`.

`command.accepted` means *validated and admitted for dispatch*, not executed.

### 7.3 Fields added by the relay to the dispatch

`sequence`, `epoch`, `authzRevision` (current authorization revision), `issuedBy {participantId, displayName}` (from the authenticated connection) and `validForMs` (validity budget). A controller cannot send them: `command.request` is strict.

### 7.4 Deduplication without re-execution ([ADR-0013](adr/0013-client-sequence-anti-replay.md))

- The relay keeps the last 256 records `commandId → (payload hash, status)` per speaker.
- Same `commandId` and same payload (including `clientSequence`) → the existing status is returned (`command.accepted` and, when final, `command.result`; or the original `command.rejected`). Never a second dispatch.
- Same `commandId` with a different payload → `COMMAND_ID_CONFLICT`.
- Unknown `commandId` with `clientSequence` ≤ the last one seen (for example an old command already evicted from the cache) → `COMMAND_EXPIRED`. That is why eviction cannot lead to re-execution.
- In the host: epochs + strictly increasing sequences + the set of `commandId`s of the epoch.
- A rejection with `retryable: true` means a **new** command (new `commandId`) may succeed later; the same `commandId` always returns the same outcome.

### 7.5 Validity and clocks

- The relay sets `validForMs` (3000 ms by default). The host measures it with its **monotonic clock from reception** of the dispatch; if it has expired when taken from the queue → `expired` (`COMMAND_EXPIRED`).
- Wall clocks of speaker, relay and host are never compared (`Timestamp` fields are informative). Real freshness is `validForMs` plus the one-way latency from relay to host, which cannot be bounded in an asynchronous network; the heartbeat/lease (§3) bounds how long a stalled link can go unnoticed (≈15 s in the host, ≈25 s in the relay).
- The relay waits for the result up to `validForMs + ResultGrace` (3 s + 3 s). Without it → `unknown` (`EXECUTION_UNKNOWN`).

### 7.6 Revalidation in the host

Before running each command the host checks its current state (from `session.updated`/`participant.updated`): live connection and lease, validity, pause (local or remote), speaker `enabled`, capability, catalog revision and parameters. If anything fails it answers `rejected` with the matching code and **does not execute**. Pausing or removing a speaker therefore discards whatever is still queued in the host.

### 7.7 Confirmation

`command.result.confirmation` says what `executed` means:

| Value | Meaning |
|---|---|
| `simulated` | Simulated backend; the system was not touched |
| `input-injected` | The OS/compositor accepted the key events. It does **not** guarantee the slide changed |
| `application-api` | The application's API accepted the call |
| `effect-verified` | The adapter observed the effect (reserved for capable adapters) |

### 7.8 Uncertainty and reconnection

- If the host disconnects (or is replaced, or restarts) with dispatched commands that have no result, those commands become `unknown`. If the host reports `failed` with `EXECUTION_UNKNOWN` (partial injection), the relay reports `unknown`.
- **Nobody retries** a command with an uncertain outcome: not the relay, not the host, not the official remote. The UI shows it and the speaker decides.
- Expired commands, or commands from older connections/epochs, are **never** replayed after reconnecting.
- After reconnecting, a client MAY ask about its pending commands with `command.status.request`. `found=false` means the relay never processed it (it did not run).
- Reconnection uses exponential backoff with jitter (host: 0.5–30 s, full jitter; remote: 0.5–15 s); a fresh `session.snapshot` follows.

### 7.9 Revocation versus execution

A command that already ran cannot be undone. There is an unavoidable race: if the host is injecting the key at the very moment the revocation arrives, that command completes. Commands still queued in the host when a revocation or pause arrives are rejected.

## 8. Action catalog

- The host announces `catalog {revision, actions[]}` in `host.register` and changes it with `host.update` (the revision MUST increase). The relay notifies everyone with `session.updated`; commands with the previous revision get `STALE_CATALOG`.
- `id` and `capability` use lowercase dotted namespaces (`presentation.next`, `presentation.navigate`) and contain no brand names.
- `parameters` is a restricted object JSON Schema: common dialect subset, local `$ref`s only (`#…`), no `$id`/`$schema`, ≤ 4 KiB. Relay and host both validate it.
- A speaker can only run announced actions whose `capability` the host granted (`defaultCapabilities` at session creation; then `PATCH participants`).
- Standard actions: `presentation.next`, `presentation.previous`, `presentation.first`, `presentation.last`, `presentation.blank` (capability `presentation.navigate`); `presentation.goto {slide}` (`presentation.jump`); `presentation.start`, `presentation.stop` (`presentation.control`). Host-defined actions use the `custom.*` namespace.

## 9. Errors

| Code | HTTP | Where | Retryable | Meaning |
|---|---|---|---|---|
| `AUTH_FAILED` | 401 | HTTP, `auth.error` | no | Wrong credential or password, or unknown/closed session (deliberately indistinguishable) |
| `AUTH_EXPIRED` | 401 | HTTP, `auth.error` | no | Token expired: join again |
| `FORBIDDEN` | 403 | HTTP, `error` | no | The role may not do this, Origin not allowed, connection replaced |
| `SESSION_CLOSED` | 410 | `command.rejected` | no | The session has ended |
| `HOST_OFFLINE` | 409 | `command.rejected` | yes | No host connected; nothing is queued |
| `HOST_NOT_READY` | 409 | `command.rejected`, `command.result` | yes | Host connected but missing permission or target |
| `SESSION_PAUSED` | 409 | `command.rejected`, `command.result` | yes | Control paused |
| `RATE_LIMITED` | 429 | all | yes | Quota exceeded; `retryAfterMs` when known |
| `INVALID_MESSAGE` | 400 | all | no | Message/body does not match the schema, or invalid parameters |
| `UNSUPPORTED_VERSION` | 400 | `auth.error`, `error` | no | Incompatible major version |
| `UNSUPPORTED_ACTION` | 400 | `command.rejected`, `command.result` | no | Action not announced/enabled |
| `STALE_CATALOG` | 409 | `command.rejected`, `command.result` | yes | Old `catalogRevision`; use the latest snapshot's |
| `TARGET_NOT_ACTIVE` | 409 | `command.result` (`rejected`) | yes | The target window is not focused or does not exist; nothing was sent |
| `PERMISSION_DENIED` | 403 | `command.rejected`, `command.result` | no | Speaker pending/disabled or lacking the capability |
| `COMMAND_EXPIRED` | 409 | `command.rejected`, `command.result` (`expired`) | no | Validity exhausted or old `clientSequence` |
| `COMMAND_ID_CONFLICT` | 409 | `command.rejected` | no | `commandId` reused with another payload |
| `EXECUTION_UNKNOWN` | 500 | `command.result` (`unknown`) | no | Cannot know whether it ran; not retried |
| `EXECUTION_FAILED` | 500 | `command.result` (`failed`) | yes | The adapter failed without applying the effect |
| `NOT_FOUND` | 404 | HTTP | no | Unknown route or participant (only after authenticating as host) |
| `INTERNAL_ERROR` | 500 | HTTP | yes | Internal error |

Error messages are safe to display: they contain no secrets or internals. Logs record a shortened session id, participant id, IP and code, never passwords, tokens or authentication bodies.

## 10. Guarantees and limits

- **Yes**: total dispatch order per session; serial execution in the host; no command runs twice because of protocol retries or reconnections; no command is replayed after reconnecting; uncertainty is reported as `unknown`.
- **No**: exactly-once external effects; effect verification for key injection; absolute freshness in an asynchronous network; end-to-end encryption against the tunnel provider ([ADR-0010](adr/0010-free-software-and-trust.md)); sessions surviving `relevo-host`.
